# DataDog Error Audit

Reads DataDog error-tracking, error logs, and (on a deep-dive) APM traces for a set of services through the `pup` CLI, and writes a diagnostic report per service. The Playbook's always-on rules apply (verify never assume, read-only for external systems unless asked, concise); this skill adds the audit procedure. Everything is scoped to `env:production` unless the user asks otherwise.

**The audit runs in two passes, and stops after the first unless the user asks for more.** The default deliverable is the surface pass: what is failing, grouped by recurrence, each issue described in a line. The expensive attribution work — walking traces to the service that actually originates a 5xx, fanning out `keru-debugging` to root-cause — is a per-issue deep-dive the user opts into, not something the first pass does for every error. This keeps the audit fast and lets the user steer depth to the issue they care about, rather than paying for a full root-cause of everything up front. It diagnoses only; it never writes a fix (that is `keru-writing-code`, out of scope). Three chains out of it:

- **Surface (the default pass):** count, group, and describe each recurring error in one line from the logs alone — enough for the user to see what is failing and decide what is worth chasing. This pass does NOT walk traces or fan out subagents; where the log does not settle whether an error is ours, its line says so (tag `UNATTRIBUTED`) rather than guessing. The report ends by offering the deep-dive on the issues that are still open questions.
- **Deep-dive, per issue, the user's to trigger:** on the user's yes for a specific issue, attribute it — walk the trace to its origin span, and if that plus a local read still does not settle it, hand it to a `keru-debugging` subagent. When the user names several issues at once, these are independent per error type, so fan them out in parallel — one subagent per issue, dispatched in a single message (Playbook "Parallelize the work", the fan-out shape). `keru-debugging` owns the reproduce -> isolate -> hypothesis+verify method; do NOT restate or re-derive it here (DRY). Each returns a validated cause (or a most-supported hypothesis with what it still needs); that is a claim to verify against the source yourself before it lands in the report, never a fact to repeat. This skill still does not fix (`keru-writing-code`) — it folds the verified cause into the attribution and upgrades the issue's tag.
- **Ticket, the user's to trigger:** once an issue has been deep-dived and is judged recurring + attributable to us, it becomes a ticket candidate and the report offers to open it. On the user's yes, chain to `keru-writing-tickets` (which produces the ticket; the actual `jira issue create` still prompts separately). Do not draft the ticket inside this skill and do not file one without that yes. Errors judged external (a downstream/partner 500 we merely surface, expected client noise) are reported as such, not ticketed.

## Tool: `pup` (read-only)

Queries run through `pup`, DataDog's CLI (see [external-tools.md](../../docs/external-tools.md) for install and auth). It emits JSON by default; parse with `jq`. Only its read subcommands are used, and only those are allowlisted; every `pup` write (`cases create`, `cases jira`, `metrics submit`, ...) is in `ask` and out of scope for this audit.

If `pup auth status` reports not authenticated, stop and tell the user to run `pup auth login` (an interactive browser OAuth flow they run themselves); do not attempt the audit against an unauthenticated CLI.

Follow `pup`'s own usage guidance: always pass `--from` on a query; count with `logs aggregate --compute=count`, never by fetching raw logs to count them; start with a small `--limit` and refine; APM durations are in nanoseconds. When a report cites a `pup` command for the user to rerun themselves, append `--no-agent` (outside this session `pup` emits raw JSON, not the agent envelope, so the citation matches what they will see).

Command shapes verified against `pup` 1.6.0 (the `--help` JSON is wrong on some of these; these are what the CLI actually enforces):

- **Time format** is bare relative (`1h`, `30m`, `7d`), an RFC3339 stamp, or a Unix timestamp. `now-7d` is rejected.
- **`error-tracking issues search`** requires `--state`, `--from`, `--limit`, and exactly one of `--track` (`trace`|`logs`|`rum`) or `--persona` (they are mutually exclusive; passing both errors). Use `--track trace` for backend services. It returns only issue `id` + `total_count`; there is no title in the search result.
- **`error-tracking issues get <id>`** resolves an id to its attributes: `error_type`, `error_message`, `service`, `file_path`, `function_name`, `state`, `first_seen`/`last_seen`. There is no `title` field; identify an issue by `error_type` + `error_message`.
- **`traces search`** returns individual APM spans (not logs) under `.data[]`, each `.attributes` carrying `service`, `resource_name`, `operation_name`, `status`, `error` (`.error.type`/`.error.message`/`.error.handling_stack`), and the linkage fields `trace_id`, `span_id`, `parent_id`. Takes `--query` (span syntax: `service:`, `resource_name:`, `@http.status_code:`, `@duration:>` in nanoseconds), `--from`, `--limit` (1–1000), `--sort`. This is the read that lets you walk a failing request across services; `traces aggregate` is its count/percentile form (`--compute`, `--group-by service|resource_name|@http.status_code`). `traces metrics` is a write (span-metric CRUD) and is out of scope. Only `traces search`/`aggregate` are allowlisted.
- **`logs aggregate`** output is at `.data.buckets[].computes.c0` (the compute is keyed `c0`), with the group value under `.by`. A `--group-by <facet>` only returns buckets when that facet is actually emitted by the service: many backend services log plain `msg`/`stacktrace` and have no `@error.type`, so grouping on it yields zero buckets. Confirm the facet exists (probe with a small query) before relying on a group-by; do not report "no exceptions" when the facet simply is not populated.
- **An empty result is data, not an error.** A `count` aggregate returns `.data.buckets: []` (no `[0]`) when nothing matches, e.g. a service that emitted only `info`/`warn` in the window. Read that as 0 errors (the service is not failing), not as a failed query. The `-status:(...)` exclusion and quoted parentheses pass through the shell inside `--query "..."` as-is.
- **`monitors search`** takes a monitor-search `--query` (NOT a log query) and returns `.metadata.total_count` plus `.monitors[]` (each with `name`, `status`, `tags`). `status` is a human string — `OK`, `Alert` (firing), `No Data` (evaluating nothing, so it cannot page). Read the state off each monitor rather than filtering the query to `status:alert`: the pre-pass needs both the firing ones and the No Data ones (a dark alarm is a coverage gap, not health). Scope by tag with `tag:(service:<svc> OR ... OR team:<team>)`; a monitor carries whatever tags it was given, so a tag you assume may match nothing (confirm before trusting a zero — see the pre-pass).
- **`slos list`** takes a free-text `--query` (matches the SLO name/description) and returns `.data[]` with `id`, `name`, `type` (`metric`|`monitor`); `.metadata.total_count` is null, count `.data` yourself. **`slos get <id>`** returns `.data.thresholds[]` (target + timeframe). **`slos status <id> --from <t> --to now`** returns the attainment for the window but errors `400 "overall denominator (total events) is 0"` when the SLO saw no events in it — that is "no traffic", not a broken query, and often means the SLO is scoped to a different env than you are auditing.

## Service set

The services to audit are a personal choice, like bot-triage's repo list. There is NO default in the repo: the list lives only in memory (see [[datadog-services]]), and only once the user has chosen to save one. It is not project config.

1. Resolve the list, in order: services named in this invocation win for this run; else the saved memory list if one exists; else ask the user, because nothing is seeded by default. Never guess service names.
2. Persist only on request: if the user asks to remember the list, write/update the `[[datadog-services]]` memory file. Do not create it unprompted.

## Procedure

Work through the audit over a time window that defaults to the **last 24h** unless the user specifies a date/range (state the window you used). The services are independent, so run the per-service gather concurrently (issue the `pup` reads for all services together and collect the results, Playbook "Parallelize the work", the I/O-concurrency shape); then group and describe each yourself. Attribution is not part of this pass — it is the opt-in deep-dive the user triggers per issue afterward. This keeps a many-service audit fast without changing what is gathered.

**The error filter (the base query):** `env:production -status:(info OR warn OR notice OR debug OR ok) service:<svc>`. Exclude the non-error levels rather than matching `status:error`, so any error severity is caught, not only the literal `error` label. The ONLY part that changes per service is `service:<svc>`; keep the rest verbatim. Pass it to `pup` as `--query "<that>"` (the parenthesized `-status:(...)` passes through the shell fine inside the quoted string).

**`env:production` is not optional, and every follow-up query keeps it.** The audit is about production customer impact, so the base query, every drill-down (by status, operation, client), and every trace-walk query all carry `env:production` — never drop it to "see more". A count that looks like a regression is often mostly non-prod: if a raw error or log count is surprisingly large, split it by `env` before you headline it (a service can log tens of thousands of uat/staging cert or TLS failures with zero in production). Report the production number; mention the non-prod bulk only as "excluded, non-prod". Audit another env only when the user explicitly asks, and then say which env every number is from.

### Monitors: firing and No Data (a domain-level pre-pass)

Error logs are not the only signal that something is failing: a service can be quiet in logs while a monitor the team already tuned is firing (an SLO burn, a latency threshold, a Temporal/Kafka backlog that emits no error line). So before the per-service log gather, run one monitors read across the whole service set and let it inform priority and attribution — do NOT report a service as healthy on a log count of 0 when a monitor for it is in `alert`.

Build the filter from the **service list you already resolved**, OR-ing their `service:` tags. Do NOT filter by `status:alert` in the query — pull every monitor for the set and read its `status` yourself, because two different states matter: `pup monitors search --query "tag:(service:<svc1> OR service:<svc2> OR ...)" --per-page 50`, reading `.metadata.total_count` and each `.monitors[]` (`name`, `status`). This is one read for the run, not per service.

- **`status:Alert` (firing) — something is broken now.** A firing monitor names, in the team's own words, what they consider broken and at what threshold. Carry it into the report and raise the priority of the service it points at. Surface it on the first pass like any error; attributing which side raises it is part of the deep-dive, on the user's yes.
- **`status:No Data` — a coverage gap, not health.** A No Data monitor is evaluating a metric that returns no series, so it *cannot page anyone* — the alarm is dark, not quiet. Treat it as its own finding: report which monitors are No Data and that the surface they were meant to watch is unmonitored, rather than reading the absence of an alert as "healthy". Common causes worth naming when you see them: the underlying metric was renamed or the service stopped emitting it (probe the metric with a small `metrics`/`traces` query to confirm zero series over the window), or the monitor is scoped to the wrong env/namespace (e.g. a Temporal monitor watching `partner-integrations-production` while real failures land in `ewa-production`, or an SLO widget querying `env:staging` — see the SLO note in Gather). A "healthy" reading that rests on a No Data monitor is unverified, not confirmed; say so.

`pup` returns the state as a human string (`OK`, `No Data`, `Alert`), so match on those values, not on a `status:alert` query facet.

A `team:<team>` tag can widen the net to monitors not tagged by service, but the team is NOT a default and is NOT hardcoded — resolve it exactly like the service list (this invocation wins, else the saved `[[datadog-services]]` memory if it records one, else ask; persist only on request). Whatever tag you use, confirm it actually matches before trusting a zero: probe once without `status:alert`, since a team's tag is often not the label you'd guess (`team:integrations` matched, `team:integrations-8lh4` matched zero). If no team is resolved, the `service:`-only filter above is enough on its own.

### Gather (per service)

- **Error volume:** `pup logs aggregate --query "<base query>" --from "24h" --compute "count"`, reading `.data.buckets[0].computes.c0`. Count via aggregate, not by listing logs. A count of 0 (the service emitted only info/warn/etc. in the window) is a real, reportable "not failing", not an error.
- **By HTTP status (the default breakdown):** `pup logs aggregate --query "<base query>" --from "24h" --compute "count" --group-by "@httpResponse.status" --sort count --limit 10`. This is the top-N-status view the reference dashboard uses (500s vs 4xx tells attribution apart at a glance). Only relied on when the facet returns buckets; a service that does not emit `@httpResponse.status` needs a different grouping.
- **Then by operation (the drill-down that localizes it):** when the status breakdown shows a real error class (the 500s, or a 4xx worth chasing), re-run the aggregate on that narrowed status grouped by operation — `pup logs aggregate --query "<base query> @httpResponse.status:500" --from "24h" --compute "count" --group-by "@operationID" --sort count --limit 10`. One operation usually owns almost all of it (extend-api's 500s over 7d: `CreateTransfer` 1115 vs a tail of 1-3), which both names the endpoint to attribute and is itself the recurrence count. Only when the service emits `@operationID`; skip if the facet returns no buckets.
- **Open error issues (the exception view):** `pup error-tracking issues search --state OPEN --from "24h" --limit 10 --track trace --query "service:<svc>" --order-by TOTAL_COUNT`, then resolve the top few ids with `pup error-tracking issues get <id>` for `error_type` + `error_message`. These are already grouped by exception, useful when raw logs lack an `@error.type` facet.
- **Spikes:** compare the window's count against a prior equal window (last 24h vs the 24h before, via `--from "48h" --to "24h"`), or an obvious jump in a status/issue count. State it as a comparison you actually ran, not an impression.
- **A specific slice** (an endpoint, a client, an operation): use the user's own log query verbatim in `--query` (e.g. adding `@httpRequest.header.x-jwt-claim-client-id:<client> @operationID:<op>` to the base), grouping by a facet that slice emits.
- **The actual error logs to analyze:** pull the recurring error's own log lines (`pup logs search --query "<base query> <narrowing>" --from "24h" --limit 20 --sort desc`) and read their `msg`, `stacktrace`, `@error`, and any `@http*` fields. The one-line description of each issue is written from these (and, on a deep-dive, attribution is judged from them too), so you need the real lines, not just the count. Keep `--limit` small (a sample is enough to see the shape); do not dump the whole set.
- **SLO burn (only when a service has an SLO and its logs look clean or a monitor points at it):** an error that is burning an error budget is worth acting on even at a low raw count. Discover the SLO with `pup slos list --query "<service name>"`, read its target with `pup slos get <id>`, and check the window with `pup slos status <id> --from "7d" --to now`. A `400 "denominator ... 0"` means the SLO saw no events in the window (no traffic, or it is scoped to a different env than you are auditing — the auto-generated dashboard SLOs are `env:staging`); resolve the production SLO id rather than reusing the dashboard's. This is optional depth, not a required per-service read; reach for it when the log pass alone does not explain a firing monitor.

Verify, do not assume: every count, spike, and top issue you report comes from a `pup` result you actually ran this session, not from memory or inference. If a service returns nothing (no errors, or no access), say so for that service rather than omitting it.

### Surface (per service, the default pass): recurrence and a one-line description

The raw count is not the finding. The first pass answers one question per service and describes the result — it does NOT attribute:

**Is it the same error, or many?** Group before concluding: N occurrences of one identical error (same `error_type` + `error_message`, or one error-tracking issue with a high `total_count`) is ONE problem, not N. Say "one recurring error, X times" rather than "X errors". A high count of a single issue and a scatter of distinct issues are very different situations; distinguish them. Describe only the recurring ones; a one-off is noise unless the user asks.

For each recurring error, write **one line the user can scan**: what it is (`error_type` + a short `error_message`), how often (the recurrence count), and a short plain-language description of what the log shows — the endpoint/operation it hits, the status, and the shape of the message. This is a *description*, not a verdict: read the log lines you pulled and say what they say, but do NOT walk traces, grep repos, or fan out subagents to decide whose fault it is. Where the log itself names the cause beyond doubt (a validation the service plainly raises, a typed 4xx the client caused), you may say so in the line; where it does not — an opaque or cross-service 5xx, a generic "500 Server Error" with no stacktrace — tag it `UNATTRIBUTED` and leave attribution to the deep-dive, rather than guessing which side raised it. The point of this pass is to let the user see everything that is failing quickly and pick what to chase, not to pre-judge it.

The report then **offers the deep-dive** on the `UNATTRIBUTED` issues (and any the user wants explained). Attribution and root-cause do not run in this pass.

### Deep-dive (per issue, the user's to trigger): attribution to the originating service

Only on the user's yes for a specific issue (or issues). This pass answers: **is it ours, or an external service's — and which service actually originates it?** Judge from the actual error lines, and say which and why. Read the `stacktrace`/`@error`/message: a stack in our code, a validation we raise, a panic we own points to us; a non-2xx from a downstream or partner call, a client sending malformed input, a dependency timeout points elsewhere. But the service that *logs* a 5xx is usually the one that *reported* it, not the one that *caused* it — an edge service surfaces a 500 that a service three hops deeper actually raised. So when the error crosses services or the log is opaque, do not attribute from the reporting service's log alone. When the user names several issues at once, fan the deep-dives out in parallel (one per issue), per the intro.

- **Walk the trace to its origin (the first move for an opaque or cross-service 5xx).** Pull a small sample of the failing spans (`pup traces search --query "env:production service:<svc> @http.status_code:500 resource_name:<path>" --from "<window>" --limit 3`), take each `trace_id`, and fetch every erroring span in that trace (`pup traces search --query "env:production trace_id:<id> status:error" --from "<window>" --limit 20`). Read the chain in call order and find the **deepest span that carries the error** — that service and `resource_name`/`operation_name` is the origin; the edge service is only the reporter. Name both in the tag (e.g. "reported by extend-api, originates in core-grpc `paymentsservice.createpayment`: `route payment: no valid vendor`"). This is cheaper and more certain than grepping blind, and it is still attribution (which service raises it), not root-cause (why it broke — that stays with `keru-debugging`).
- **Sample honestly.** A handful of traces is a sample, not a census: when you report a split across origins ("2/3 traces originate in core-grpc, 1/3 in core-rails"), state it as a share of the sampled traces and say how many you walked, not as an exact count of all failures. Widen the sample only if the first few disagree.
- **Then confirm the code path locally.** Once the trace names the origin service, prefer the local clones under [[projects-root]] (`~/Documents/GitHub`) to confirm which code path in *that* service emits the message — grep it there over more `pup`/API calls (the same service often spans multiple repos). If the repo is not cloned, note that rather than guessing. Skip the trace walk only when the error is self-contained and the log already names the cause (a validation the reporting service itself raises, a typed 4xx); walking a single-span trace tells you nothing new.
- This is a light attribution pass (which side, which service raises the error), not a root-cause investigation. If the trace walk plus a local read still does not settle it, hand that error to a `keru-debugging` subagent rather than doing the deep reproduce/isolate here (DRY, that is debugging's method); its verified cause, once you confirm it against the source, upgrades the tag from UNESTABLISHED to OURS/EXTERNAL. An error still unsettled after debugging (could not reproduce, no single confirmed cause) stays UNESTABLISHED, carrying debugging's most-supported hypothesis.
- Never assert a cause the evidence does not support. "Ours", "external", and an origin service are all claims you must be able to point at (a stack frame, a downstream status, a repo line, or the deepest erroring span in a named trace).

A ticket candidate is an error that has been deep-dived and is both **recurring** and **attributable to us** (or otherwise needs our action). A firing monitor or a burning SLO on a service is itself "needs our action" even when the raw log count is low — the team already set that threshold — so treat it as a candidate on the same footing, attributing it the same way (which side raises it). A No Data monitor is also a candidate: the fix is different (restore the metric or repoint the monitor, not fix an error) but it is still our action, so mark it. External and unestablished errors are reported with their tag but are not candidates. An `UNATTRIBUTED` error that has not been deep-dived is not yet a candidate — the deep-dive is what tells you whether it is.

## Output

Write the report to `/tmp/keru-deliverable-datadog-audit.md` first (the Playbook's gated-deliverable rule; a PreToolUse gate validates it before the file is written). Your chat reply is a link to that file plus at most one line, not its pasted contents. (The audit spans a service set, not one ticket, so no `<id>` suffix; a new audit replaces the last.)

Lead with substance. Open with a one-line **Monitors:** roll-up so the team's own alarms lead, naming both states: firing (`<name> (<service>)`) and No Data (`<name> (<service>)` — coverage gap), or "none firing, none dark". Then the per-service sections, ordered worst-first (a firing monitor or a real spike at the top, then highest volume). Use this shape per service:

```text
**<service>**  <- firing: <monitor name> | No Data: <monitor name> (coverage gap) | (no line if none)
Volume: <count> errors over <window><, spiking vs <baseline> | , flat>

- <error_type>: <short error_message>, one recurring error x<count> — <one-line plain-language description of what the log shows: the operation/endpoint, the status, the message shape> [UNATTRIBUTED: not yet deep-dived | CLIENT/EXTERNAL: <the log itself names it — a typed 4xx the client caused, a plainly-external status>]
- <next issue...>
```

On the surface pass, most 5xx and cross-service errors carry `UNATTRIBUTED` — the description says what the log shows, not whose fault it is. A tag beyond that on the surface pass is only for errors the log settles on its own. Once an issue has been deep-dived (below), replace its line with the attributed form:

```text
- <error_type>: <short error_message>, one recurring error x<count> [OURS: <the stack frame / repo line, or — for a cross-service 5xx — "reported by <svc>, originates in <origin svc> <resource>: <msg>" from the trace walk; or the cause keru-debugging confirmed> | EXTERNAL: <the downstream status / client cause> | UNESTABLISHED: still unsettled after a keru-debugging pass, with its most-supported hypothesis]

Ticket candidates (deep-dived issues only): <error_type> (recurring + ours) | <monitor/SLO> (firing or No Data) | none yet — run a deep-dive first
```

Keep it scannable: counts, issue identifiers, and either the one-line description (surface) or the attribution tag with its one-line evidence (deep-dived), no per-line prose. When a 5xx was attributed by walking traces, cite the origin span (service + resource) and, if you reported an origin split, the sample size (e.g. "2/3 sampled traces"). If a service returned nothing or was inaccessible, keep its header with that one line so the gap is obvious. End with one line stating the window audited. If nothing is failing across all services (no errors, no firing monitor), say that plainly — but if a service's "healthy" reading rests on a No Data monitor, flag it as unmonitored rather than confirmed-healthy.

After the file is delivered, the chat line offers the **deep-dive** on the `UNATTRIBUTED` issues (name them, or "which issue do you want attributed?"). Only on the user's yes, run the deep-dive for that issue (a separate turn) and update its line in the report. A ticket is offered only *after* an issue has been deep-dived and comes out recurring + ours; on that yes, chain to `keru-writing-tickets` (a separate turn/skill), and do not draft or file it otherwise. Do not attribute, root-cause, or offer a ticket for an issue the user has not asked to deep-dive.

## Scope and safety

Read-only on DataDog, always. Never create a case, submit a metric, or run any `pup` write; those are remote mutations in `ask` and are not part of this audit. The local repo reads for attribution are read-only greps of existing clones, not clones or writes. Filing a ticket is a separate step via `keru-writing-tickets` on the user's yes (and `jira issue create` still prompts on its own); this skill produces the report and the offer, not the ticket.

## Before delivering

**Surface pass (the default deliverable):** Confirm every service in the resolved list was audited (or its no-data / access error reported), the monitors pre-pass ran once for the set built from the resolved services and read both firing and No Data states (and, if a team tag was used, it was confirmed to match so a zero is real — the team was resolved, never assumed; a No Data monitor was reported as a coverage gap, not folded into "healthy"), the window is stated, every count, spike, and monitor state came from a `pup` result run this session (not memory, Playbook "verify"), and each recurring error carries a recurrence count and a one-line description drawn from log lines you actually pulled. Confirm you did NOT attribute, walk traces, or fan out subagents in this pass: an opaque or cross-service error is tagged `UNATTRIBUTED`, not guessed, and the report offers the deep-dive rather than a ticket. Then stop and wait for the user to pick an issue.

**Deep-dive pass (only for issues the user asked to attribute):** Confirm each cross-service or opaque 5xx was attributed by walking the trace to its origin span (not from the reporting service's log alone), any origin split was reported as a share of the sample with its size stated, and the attribution tag's one-line evidence is something you can point at (a stack frame, a downstream status, a repo line, or the deepest erroring span in a named trace; no asserted cause the evidence does not support). Confirm any error still in doubt after the trace walk got a `keru-debugging` subagent and that any cause it returned was verified against the source before you tagged it (not repeated on the agent's word). Then stop; do not root-cause an error yourself outside that subagent (debugging owns the method), do not write a fix (`keru-writing-code`), and do not draft or file the ticket without the user's yes.
