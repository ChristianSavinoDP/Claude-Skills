# Writing Code

Procedure for implementing a code change. The Playbook's always-on rules still apply (verify before delivering, stay in scope, right tool not raw shell, safety); this skill adds the code-specific rules and steps.

## Before coding

1. Get the ticket and its context first (Playbook "first step"). Use the `keru-gather-context` skill to gather the ticket and its full chain (read-only) as the source of truth: linked issues, parent/epic, and, if the ticket came from an investigation, that investigation's ticket AND its PR/document. Do not start coding until that skill's gate passes. Scope and acceptance criteria come from it.
2. Read the surrounding code and existing patterns before writing, so the change matches what is there. Reuse what exists instead of adding new.

## Code-specific rules

- **Comments: default to none** (the Claude-Skills repo's own scripts are the exception: they carry their design rationale on purpose, and the gate skips them). Write the code with no comments, then add one back only where a competent reviewer could not infer the *why* from the code and its names (an arbitrary-but-fixed tie-break, why an error is permanent rather than retryable, a constraint imposed by another system). One short line, never a block, never one per declaration; docstrings and doc comments count, and tests get the same bar (the test name already says what it checks). A doc comment the repo's linter actually requires (read its config) stays, as one line. No ticket or PR references (`DBI-1234`, `#2237`): they age into dead links, so the why must stand on its own; ticket context goes in the PR description and the commit. This overrides the neighbors: a densely commented file, or a repo guide telling you to match its density, is not the bar (the one exception to the Playbook's "Follow existing patterns"); an explicit request from the user is. `keru-gate-comments` is a mechanical backstop for the part a parser can check (limits in [docs/permissions.md](../../docs/permissions.md)): passing it does not make a comment acceptable, and when it denies, cut, do not reword or split to fit; if what it blocked is a linter-required doc comment or one the user asked for, tell the user instead. A comment's *why* is also a claim held to the verify bar: if you cannot point to the line that proves it, it does not go in.
- **Reuse existing packages.** If a package, helper, or utility exists for what you need, use it; do not write a parallel implementation.
- **Follow the reference code's reusable shape.** When you model new code on existing code, match how that reference is structured. If the reference lives in a shared/reusable package, write yours the same way, not as an inline copy buried in one caller.
- **Match the file's naming, style, and idioms** (read a neighbor before writing).
- **Keep the file's declaration order.** Place new declarations following the order the file already uses (e.g. exported types and constructors first, unexported helpers grouped at the bottom). Do not impose an order the file does not have; read a neighbor before deciding where code goes.
- **Tests for non-trivial new logic.** When you add logic with branches, edge cases, parsing, or anything whose failure only surfaces at runtime, add unit tests in the same PR, following the repo's existing test pattern, and tell the user you did and why. Two limits: only if the repo already tests that kind of code (do not introduce a framework where there is none), and not for trivial changes (config, rename, wiring). The first test drives the property the design's safety rests on (the failure branch it claims to handle, a retry that must fire, a partial result that must not pass as complete), not the happy path. For logic that compares, matches, classifies, or detects change, list the input shapes it must tell apart as table-driven cases (the input-shape table), one row per shape, starting with real inputs from the gather-context map's inputs line (for change detection: two consecutive real values that differ but must not trigger); a fix proven only on the case that triggered it is not proven. Assertions that only count the happy path (exact counts, "it returned two events") leave the risk untested. If the user says no tests, skip them.
- **Do not silently drop existing behavior.** Removing or changing behavior something may depend on (a retry, an error path, a fallback, a default) is a serious change, not a cleanup: call it out and confirm it is intended.
- **Human-facing text says what the code observes, not the cause it presumes.** When authoring an alert, log, error message, or comment, separate what is measured from what may have caused it. A symptom-based check (running-vs-desired tasks, healthy-host count) must not claim to detect the root cause; describe the symptom and list possible causes instead.
- **A doc shipped with the change is a deliverable, not a byproduct.** If the change includes a doc alongside the code (a runbook, README, an access or reference doc, an ADR fragment), do not write it straight to the repo: a doc written directly bypasses every form and verification gate, which is how em dashes and unverified claims ship. Decide what it must say and keep it minimal (document only what is verified and exists; defer not-yet-built behavior to its downstream ticket rather than describing it speculatively), then hand it to the `keru-writing-docs` skill (mode `companion`) with the sources it must be verified against, to check every claim against its source, enforce the form rules, and write it to its home. The prose in a doc is a claim held to the same bar as a line of code; there is no "it is just a doc" exemption.

## Before delivering

Run the Playbook's verify gate: re-read the full diff as a strict reviewer (Copilot included) would and fix what they would flag, especially bugs that compile but fail at runtime (struct tags/`omitempty`, config parsed at runtime, nil, edge cases). Confirm the change satisfies the acceptance criteria and nothing beyond them.

**Re-walk the map against the final diff.** The gather-context map (inputs, outputs, runtime, upstream, precedent) was drawn before you wrote code. Every input, output, external call, and dependency the diff ended up with must be on it, with its source opened at the moment you rely on it: what you added while implementing (a new call site, a new emitted state, a new job, a new event produced) is exactly what the earlier map does not cover. Open the callers of anything whose output you changed, because "correct in isolation" is not "the caller does the right thing with what it now returns". When the ticket flags a symbol as constrained (a getter being retired, a field deprecated, a pin that will not compile past its next bump), grep your own diff, tests included, for new uses of every generated form of it (field, getter, constant, JSON name).

**Run the repo's own checks, not a proxy for them.** Your verify gate is the exact checks the repo and its CI enforce, discovered from source (`Makefile` targets, `.golangci.yml`, the CI workflow), and actually run before you deliver: e.g. `make lint-local` / `golangci-lint run`, not `go vet` alone (`go vet` does not run staticcheck, so it misses rules like ST1005). A hand-picked subset you assume is equivalent is not the gate; read the config to know what actually runs, then run that.

**After merging the base branch, re-read both sides and re-run the checks: a clean auto-merge is textual, not semantic.** Git resolving a file without conflict markers means the lines did not overlap, not that the combined result is correct. A resolution that only deletes the markers can ship a broken build (the base added a test that calls your changed function with its old signature) or a silently drifted contract (the base's new gate combined with your ungated path, so a metric now counts the wrong thing). After any merge, re-read the full body of every function both sides touched and the tests both sides changed, then re-run the build and the repo's own checks; the markers being gone is not evidence the merge is right.

### Adversarial review before delivering (non-trivial changes)

For any change with real logic, infra, or CI (not a rename/config one-liner), do not rely on your own re-read alone: you are blind to your own decisions. Fan out fresh subagent reviewers over the diff (Playbook "Parallelize the work", the fan-out shape), with no stake in how you wrote it, to hunt for what authors miss and Copilot catches. Scope each reviewer to the **full body of every function the diff touches, not just the changed hunk**: a pre-existing defect (an ignored `err`, a missing escape) inside a function you edited is in scope the moment you touch that function, and a hunk-scoped read walks straight past it. And scope **at least one reviewer to the callers of the changed code, the contracts its outputs feed, and the runtime it runs in** (hand it the gather-context map as re-walked against the final diff), not only the functions you edited: the bug that blocks the merge usually lives in a file or a repo your diff never touched, and a review scoped to the diff cannot see it. Dispatch them in a single message, each owning one dimension and returning `file:line` plus why. All four dimensions are judgment (Playbook "Match the model to the leg"), so every reviewer runs on the session's model: no `model` override, and no agent type that pins a cheaper one. **Run all four dimensions below**; skipping one is allowed only when it is provably not applicable, and then you state which and why. A dimension that stalled, hit its watchdog limit, or returned a fragment is neither a skip nor a degraded pass, it did not run (Playbook "Parallelize the work"): re-launch it read-only and block delivery until it returns, because correctness is exactly the dimension whose stall hides the bug that ships. Cherry-picking two of the four (correctness and tests, dropping references and human-facing text) or dropping the caller-scoped reviewer is exactly how a wrong log line and a caller-contract bug reach the human reviewer.

- **Correctness / runtime bugs:** ask two separate questions of every path: *can it crash* (nil, panic, deref) and *can it return a wrong-but-valid answer* (a truncated page returned as if complete, a partial result treated as the full set, an opaque server value fed back unescaped). "Breaks safely / does not crash" is not "returns the right result"; hunt the second as hard as the first. Also: dead or now-unused code left beside an edit (e.g. a permission/scope still granted after its use was removed), checks that do not actually cover their case (e.g. `git diff --exit-code` missing untracked files), behavior silently dropped, config parsed at runtime, and other bugs that compile but fail at runtime.
- **Test quality:** flaky tests, assertions that depend on timing, real `sleep`/wall-clock, or goroutine scheduling rather than a deterministic signal (the kind that pass locally and fail in CI).
- **References and external refs:** mutable or inconsistent external references (a `@main` ref where the repo pins versions); references that do not resolve, a path, URL, or runbook link the change emits that does not exist on the base branch, with the cross-PR merge-order dependency not flagged.
- **Human-facing text:** an alert, log, or error message (or a code comment) that overstates behavior, asserting a cause or downstream effect the code does not actually observe (a symptom-based check, e.g. running-vs-desired tasks or healthy-host count, described as detecting the root cause), and any comment that fails the comment rule above.

Then, critically: **validate each finding against the real code before acting on it.** When the agents return, collect their findings, open the file, and confirm each issue is actually present, do not accept or dismiss a finding from assumption (that is the exact failure this guards against). Apply the confirmed ones and re-review. Aim to catch what a reviewer like Copilot would, before delivering, not after.

Two triage traps that let confirmed findings ship anyway, both are banned:

- **"Pre-existing pattern / consistent with the neighbors" is not a reason to dismiss.** That discount is only valid when the change does not alter reachability. If your edit makes a latent issue newly reachable (a new pagination loop that feeds a server-controlled cursor back into a URL, a new caller-controlled value flowing into an unescaped param) it is in scope and yours to fix, no matter how many neighbors share the pattern. The reviewers will usually say so out loud; when they do, that sentence is the finding, not a footnote. **A finding that actually touches the code's behavior gets analyzed harder, never waved off as a nit or "pre-existing".** *Where* a bug's code lives is not *when* it became reachable: "the bug is in old code, so it is old" is the trap. Before you label anything pre-existing, prove your diff did not change its reachability, and any change of cardinality on something concurrent or shared (1→N workers on one `WaitGroup`, 1→N writers, 1→N callers of a path with partial-failure behavior) is a reachability change until you have traced the failure modes and shown otherwise.
- **Weight an independent reviewer's severity above your own authorship bias.** When a fresh reviewer rates something and you want to downgrade it, the burden is on you to *refute their argument at the code*, not to invoke consistency or your intent. If you cannot refute it, their severity stands.

**A confirmed finding is a blocker to resolve, not a note to ship with.** Flagging a risk in a code comment or PR note is not resolving it: "keep this below X" written next to a value that is not below X is still a bug. If the review confirms a value is wrong (e.g. a timeout exceeds the pod's grace window), verify the real constraint at its source and set a safe value before delivering; do not ship the suspect value with a TODO-style comment, and do not reclassify it as an "infra prerequisite out of scope" when the constraining value is readable via `gh` or a local clone (that is the gather-context map's runtime line, do it). The value leaves your hands correct, or it does not leave. If you consciously choose not to fix a confirmed finding, that is an explicit, argued exception, and it must at minimum appear in the PR description; silently dropping it is not allowed.

**When the change references an in-flight artifact, flag the merge-order dependency.** If the diff emits a path, URL, or runbook link that only resolves once another unmerged PR lands, state that dependency explicitly to the user and in the PR description; do not link and move on. A reference that 404s on the base branch until something else merges is non-actionable if this change lands first.

**Report what the review actually covered, not a clean bill.** When you tell the user or the PR the outcome, state what was in scope and what was not: which dimensions ran, whether the callers and contracts the change's outputs feed were opened, and, for logic that compares, matches, or classifies, whether its input-shape table exists as tests. "Build green, lint clean, two adversarial reviews, no bugs" is evidence about the lines you touched; it is not evidence about the contracts those lines depend on, and reporting it as a clean bill when the review never opened the caller is the false confidence that hands the reviewer a PR that looks verified and is not. If a caller or contract was not read, or a dimension was skipped, say so plainly instead of implying a clean pass; distrust your own "no bugs" precisely when the scope excluded the caller.

Then stop; do not offer to commit.
